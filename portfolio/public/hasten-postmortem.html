Hasten postmortem

Four architectures in one month to reach an app with no backend and no language model. This is what was built, what was removed, and what the record does and does not explain.

  • RoleSole developer
  • Commits157, 44 with Claude Code
  • Tests325 Jest, 16 device flows
  • Shipped stackExpo, SQLite, on-device NLP

Summary

Hasten is a local-first mobile app. You capture a thought by voice or text, and an on-device pipeline segments it, extracts entities, dates and urgency, classifies it, and ranks it into a plan. Nothing leaves the phone.

The product requirement was fixed from the first week: work fully offline by default, with always-on cloud AI processing listed as a non-goal. Two of the four architectures I built violated that requirement, and both were removed.

What went wrong

  • Cloud parsing contradicted the product's own constraint. The Gemini parser and the Phi-3 server both required a network path, which the offline requirement ruled out. Both were built, and both were removed.
  • The first Expo build was unstable in Expo Go. Reanimated and worklets version conflicts were fixed first by pinning versions and then by removing the gesture and animation stack altogether.
  • Two framework migrations were made without a written decision. The history shows the move to Flutter and the return to Expo, and records no rationale for either, so I can't cite one here.
  • The evaluation harness did not survive the last rewrite. The Dart eval tools and the labelled dataset were deleted with the Flutter code, so the current tree has no evals.

What held across every rewrite

The pipeline design did not change: segmentation, extraction, classification, ranking. The classifier was built in three phases and carried forward intact: weighted rule matches plus prototype-token similarity, then learning from user corrections, then a confidence-aware review screen. Feedback is capped per token and confidence is clamped to a fixed band, so a single correction has a bounded effect.

Evidence

Heuristic tuning was measured against a labelled dataset. Category accuracy rose from 50.85% to 77.58% (English 81.33%, French 68.75%), due-date recall from 70% to 100%, and people recall from 0% to 100%. The changes were word-boundary matching, a case-sensitive people pattern and the removal of ambiguous keywords.

These figures are self-reported from a commit message. Because the eval tooling was later removed, they cannot be reproduced from the current repository.

What can be verified today: 325 Jest tests (251 unit, 74 component) and 16 Maestro device flows covering smoke, review, onboarding, accessibility regression, jank, and seeded runs at 1,000 and 5,000 items. A physical-device certification run surfaced 8 failures, all fixed, including handling for a full SQLite disk.

What I would change

  • Port the eval harness before the product code. A rewrite that cannot be measured against the previous version is a regression risk with no detector.
  • Write a decision record for every architecture change, even a three-line one, at the time of the change.
  • Run tests in CI. The repository's only workflow dispatches to a separate quality repo. Type checks and the Jest suite run locally and should gate every pull request.
